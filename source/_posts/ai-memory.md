## 它想解决什么问题

你的编码 Agent 大概已经有记忆功能了——Claude Code 自己记笔记，Cursor 也记点东西。但它们都有同一个极限：**笔记躺在一台机器上、属于一个 Agent、换工具就失忆**。

现实里这很要命：Claude Code 跑到一半 token 用尽，你想换 Codex 接手，结果新 Agent 完全不知道架构长什么样、哪些方案试过失败了、还有哪些问题没解决。

## 核心机制拆解

**1. 六个"跟着你走"。**

- **跨 Agent**：Claude Code、Codex、Cursor、Gemini CLI、OpenCode、Grok、Devin、Kimi、Kiro 等 20+ harness 喂同一份记忆；交接单是**类型化协议**，每条有 owner，只被认领一次——避免两个 Agent 同时抢同一个待办；
- **跨会话深度**：`ai-memory run` 启动的 Agent 不仅拿到共享工作流，还能拿到私有、临时的本地历史投影；
- **跨项目**：你的工作习惯小档案（包管理器、测试布局、架构偏好）在每个新仓库会话启动时就位，不用反复自我介绍；
- **跨机器**：记忆存在你自己跑的服务器上——同一台笔记本、homelab 或任何地方。

**2. 隐私边界画得很清楚。** 远程服务器只接收 harness 与会话身份，**永远不接收本地转录文本**。这一点值得强调：多数"云端记忆"方案的第一性原理是"把对话传上去"，而它反过来了。

**3. Rust 单二进制。** 没有运行时依赖、没有守护进程集群——一个可执行文件就能当记忆服务端，部署成本接近零。这也是它敢承诺"跨机器"的前提。

## 点评

**亮点**是抓住了"记忆的归属"这个真问题。记忆功能各家都有，但都是围墙花园；把记忆做成中立基础设施，并用类型化交接单解决并发接管，工程判断很到位。

**局限**：1.3 万星的项目生态还在早期，20+ harness 的适配深度必然不均；跨机器同步意味着你必须自己维护一台服务端，对纯个人用户是额外负担；"交接单"的价值取决于 Agent 是否真的会读它，各 harness 的注入时机差异需实测。

适合人群：多 harness 混用的开发者；长周期项目（跨周跨月与同一代码库较劲）；想把"AI 会话里学到的东西"沉淀成团队资产的工程团队。
